# Работа с Git

`main` — основная ветка с согласованной работой команды. Каждую задачу делаем в отдельной ветке и вливаем через Pull Request (PR) после проверки другим участником. Прямые push и force push в `main` по договорённости не используем.

## Обычная задача

Начинайте с чистой рабочей директории. Если есть незавершённая работа, сначала сохраните её в своей ветке.

```sh
git fetch origin
git switch -c feat/task-name origin/main
# Внесите изменения и выполните проверки, подходящие для задачи.
git add path/to/changed-file
git commit -m "feat: describe the change"
git push -u origin feat/task-name
```

Откройте PR из своей ветки в `main`. Опишите результат и выполненные проверки, назначьте рецензента. Автор учитывает замечания; после одобрения объединяем PR через Squash and merge, если этот способ доступен в репозитории. В сообщении итогового коммита сохраняем суть задачи. Отдельную общую `develop` пока не вводим.

Для исправлений используйте `fix/task-name`, для документации — `docs/task-name`, для служебных изменений — `chore/task-name`. Ветки агентов могут иметь префикс `codex/`.

Не добавляйте ключи API, токены, `.env`, локальные окружения и тяжёлые результаты слайсинга в коммиты. Перед коммитом просматривайте `git diff --cached`. Не переписывайте общую историю.

## Текущее ограничение защиты

На момент подготовки документа `neF1anders/mosprom` — приватный репозиторий личного аккаунта, `main` не защищена. У нашего аккаунта права `WRITE`, без администрирования репозитория. Описанный порядок — договорённость команды: технического запрета на прямой push сейчас нет. PR-шаблон, CI и локальные Git hooks сами по себе такого запрета не обеспечивают.

Для серверной защиты приватного репозитория GitHub требует подходящий платный тариф: GitHub Pro для личного аккаунта владельца или GitHub Team для организации. Бесплатно защита доступна для публичных репозиториев. Переводить проект в публичный ради этого без решения владельца не нужно.

Когда тариф позволяет, владелец настраивает защиту `main`:

- Требовать PR и минимум одно одобрение другого участника.
- Сбрасывать одобрения после новых коммитов и требовать закрытия обсуждений.
- Запретить обход требований, включая обход администраторами, прямой force push и удаление ветки.
- Когда появится CI, добавить его реальные обязательные проверки.

На бесплатном тарифе организации можно разграничить доступ к репозиторию целиком, оставив запись только интеграторам. Это не защита отдельной ветки и потребует другого процесса передачи изменений. В приватном репозитории личного аккаунта приглашённые collaborators имеют и чтение, и запись.

Источники: [защита веток](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [права в личном репозитории](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/permission-levels-for-a-personal-account-repository).
