# Правила работы

## Git и ревью

`main` — основная ветка с согласованной работой команды. Каждая задача выполняется в отдельной ветке и оформляется через Pull Request (PR). Прямые push и force push в `main` не используем. Сливать PR в `main` может только Максим Пугачев (@Maksim339).

Начинайте новую задачу с чистой рабочей директории:

```sh
git fetch origin
git switch -c feat/task-name origin/main
# Выполните задачу, обновите реестр фич и проверьте изменения.
git add path/to/changed-file
git diff --cached
git commit -m "feat: describe the change"
git push -u origin feat/task-name
```

Используйте `feat/` для фич, `fix/` для исправлений, `docs/` для документации, `chore/` для служебных задач. Ветки агентов могут иметь префикс `codex/`.

В PR кратко опишите результат и проверки. Всегда тегайте @Maksim339 для ревью и назначайте Максима рецензентом. После исправления замечаний Максим проверяет результат и объединяет PR. Для собственного PR Максим запрашивает ревью другого участника; слияние всё равно выполняет Максим.

## Код

- Не оставляйте мёртвый код: неиспользуемые функции, импорты, недоступные ветки, закомментированные реализации и устаревшие обходные решения удаляем.
- Перед новой реализацией проверяйте существующий код. Общую логику переиспользуйте; дублирование выносите в понятные функции или модули. Не создавайте абстракции «на будущее» без текущего применения.
- При добавлении или изменении фичи проверяйте, какие существующие сценарии она затрагивает. Старые фичи должны продолжать работать.
- При исправлении бага сначала воспроизведите его и установите корневую причину. Устраняйте её, а не маскируйте симптом обходными условиями, подавлением ошибок или случайными задержками. Добавьте регрессионный тест, который воспроизводит баг до исправления и проходит после; проверьте связанные сценарии.
- Не добавляйте в Git секреты, `.env`, локальные окружения и тяжёлые результаты слайсинга.

## Реестр фич

Ведём короткую таблицу в [docs/FEATURES.md](docs/FEATURES.md): идентификатор, пользовательская возможность и E2E-проверка.

- Новую фичу добавляйте в реестр в том же изменении, что реализацию и её E2E-тест.
- При изменении поведения обновляйте строку и соответствующие тесты.
- При удалении фичи удаляйте строку, её тесты и оставшийся неиспользуемый код. Зависимые сценарии обновляйте и проверяйте.
- Планы и нереализованные возможности в реестр не включаем.

## E2E и завершение выкладки

Каждая фича из реестра должна иметь E2E-проверку пользовательского сценария. Новые тесты дополняют регрессионный набор; нельзя отключать или ослаблять проверки существующих фич ради прохождения новой.

После каждого push CI должен запускать полный набор E2E, покрывающий все фичи из актуального реестра. Это относится и к push в ветку задачи, и к коммиту после слияния в `main`. Зелёный прогон предыдущего коммита не засчитывается.

Выкладка считается завершённой только после успешного E2E-прогона для выкладываемого коммита в целевом тестовом окружении. Если тесты упали, не запустились или обязательное окружение недоступно, проверка не пройдена и выкладка не завершена. Изменения документации и структуры также не должны ломать существующие сценарии.

Полный набор запускается командой `uv run --locked python scripts/run_tests.py` (нужны `npm ci` и `npm run build` в `src/web` и Chromium для Playwright). Скрипт сам поднимает тестовый провайдер, заглушку STE Slicer и приложение на отдельной SQLite. CI выполняет его на каждом push и PR. Набор включает Python-проверки, компонентные тесты и браузерные сценарии; пустой набор тестов подтверждением работоспособности не считается.
