# Конвейер этапов 1, 2 и 3

После готовой карточки задание проходит подбор параметров (этап 2) и его проверку (этап 3). Если проверка просит изменений, подбор делает ещё один заход, и проверка смотрит его снова. На этом конвейер останавливается. Слайсинг будет следующим шагом.

```
сообщение ─► stage1.run ─► карточка готова? ─нет─► waiting_user
                               │да, в той же транзакции
                               ▼
            stage2.select_parameters (одна задача)
              подбор, заход 1 ─► проверка 1 ─► ok ───────────────────────► completed
                                     └─► замечания ─► подбор, заход 2 ─► проверка 2 ─► completed
```

## Состояние задания

| Поле | Значения |
| --- | --- |
| `status` | между этапами `queued`, во время шага `running`, в конце `completed`. «Стоп», удаление и правка работают теми же переходами, что у этапа 1 |
| `stage` | `understanding`, `parameters`, `validation`, `done` |
| `parameters` | краткий итог последнего набора: заход, режим, профиль, материал, сколько настроек изменено, сколько требований не выполнено, итог `pending`, `ok` или `attention` |

`attention` ставится, если после последнего захода проверка всё ещё нашла замечания, подбор не смог выполнить требование или деталь не помещается в режим. Пользователь видит итог в ленте и в строках таймлайна. Правка в чате запускает новую ревизию с этапа 1, ответы агентов при этом берутся из кеша.

## Как работает задача

`src/backend/pipeline/parameters.py`, порядок шагов решает `next_step` в `src/backend/domain/pipeline.py`.

- Оба шага детерминированные и быстрые, поэтому идут в одной задаче, а не передаются через очередь. Каждая передача через очередь с той же блокировкой ждала бы опроса Procrastinate до 5 секунд. Отдельной задачей станет слайсинг: ему нужна машина со слайсером.
- Перед каждым шагом и при записи его результата проверяется, что ревизия текущая и не нажат «Стоп» (`pipeline/store.py`).
- Подбор и проверка вызываются в отдельном потоке и ограничены таймаутом, чтобы не останавливать цикл событий воркера.
- Результат каждого шага лежит в таблице `stage_results`, один на ревизию, шаг и заход. Повторно доставленная задача берёт готовые шаги оттуда.
- События `parameters.started|completed`, `validation.started|completed` (с `data.iteration`) и `pipeline.completed` двигают таймлайн чата.

## Контракты

| Что | Где |
| --- | --- |
| Карточка задания 2.0 | [TASK_CARD.md](TASK_CARD.md), [task-card-v2.0.schema.json](task-card-v2.0.schema.json) |
| Набор параметров `stage2.parameter_set` 0.2 | [parameter-set-v0.2.schema.json](parameter-set-v0.2.schema.json), модель `ParameterSet` в `src/backend/domain/parameters.py` |
| Обратная связь проверки `stage3.feedback` 0.1 | [stage3-feedback-v0.1.schema.json](stage3-feedback-v0.1.schema.json), модель `Feedback` |
| Коды требований для этапов 1 и 2 | `knowledge/requirement_keys.json` |
| Файлы выданной сборки STE Slicer 5.2.4 | `knowledge/ste_5.2.4/`, читается в `Catalog` (`src/backend/domain/catalog.py`) |

`GET /api/v1/jobs/{id}/parameters` отдаёт последний набор текущей ревизии, тот же JSON скачивается из чата.
