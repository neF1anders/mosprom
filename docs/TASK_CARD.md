# Карточка задания 2.0, контракт этапа 1 и этапа 2

Карточка `TaskCard` версии **2.0** это единственный результат первого этапа. Машиночитаемая схема лежит в [task-card-v2.0.schema.json](task-card-v2.0.schema.json), тест `tests/backend/test_schema.py` следит, чтобы она совпадала с кодом. Что из карточки читает подбор параметров, описал его автор в контракте [stage1-contract.md](stage1-contract.md) ([схема](stage1-contract.schema.json)); тест `tests/backend/test_requirement_codes.py` проверяет собранную карточку по этой схеме.

## Как второй этап получает карточку

Когда у карточки нет блокеров, первый этап в одной транзакции сохраняет её, переводит задание в `queued` на этап `parameters` и ставит задачу Procrastinate:

```
task: stage2.select_parameters   queue: stage2   lock: job:<job_id>
args: {"job_id": "...", "revision": 7}
```

Обработчик (`src/backend/pipeline/parameters.py`) берёт карточку текущей ревизии и проходит подбор параметров и его проверку. Как это устроено, описано в [PIPELINE.md](PIPELINE.md). Если пользователь успел изменить задание, новая ревизия отменяет ждущие задачи старой, а уже идущий шаг старой ревизии останавливается на охране ревизии. Карточка доступна по `GET /api/v1/jobs/{id}/card`.

## Поля

| Поле | Содержание |
| --- | --- |
| `schema_version`, `job_id`, `revision` | версия контракта и ревизия задания |
| `purpose` | назначение детали |
| `requirements[]` | требования: `key`, `label`, `value`, `unit`, `conditions`, `mandatory`, `provenance`, `sources[]`, `verified`, `superseded[]` |
| `preferences[]`, `production_constraints[]` | пожелания и ограничения производства |
| `assumptions[]` | допущения: `text`, `basis`, `consequence`; это не требования |
| `unknowns[]` | что неизвестно |
| `questions[]` | все вопросы с ответами пользователя |
| `geometry` | сводка анализа STL (габариты, дефекты, объём только когда он достоверен) |
| `stl_analysis` | полный отчёт анализатора активного STL без сокращений, `attachment_id`, `sha256`; с версии отчёта 1.2 в нём есть нависания, кандидаты ориентации и ось вращения ([STL_ANALYSIS.md](STL_ANALYSIS.md)) |
| `verdict` | всегда `null`: судьи больше нет, поле оставлено ради совместимости |
| `readiness` | `ready`, `preliminary` (есть допущения, неизвестные или дефекты) или `blocked` |
| `allowed_actions`, `blocked_actions` | `select_parameters` и причины блокировки |
| `files[]`, `versions` | исходные файлы с sha256; версии правил, анализатора, словаря кодов (`requirement_keys`), модели и промптов `gate`, `interpreter`, `checker` |

### Источники требований

`sources[].source_id` это стабильная ссылка: `<attachment_id>:<страница>` для файлов, id сообщения для чата, `answer:<question_id>` для ответа, `kb:<record>` для базы знаний, `assumption` для выведенного значения. Поле `method` устанавливает сервер по виду источника:

- `text` значит, что значение взято из текста документа;
- `vision` значит, что значение прочитано со страницы без текстового слоя;
- `user` значит, что значение пришло из сообщения или ответа пользователя;
- `knowledge` значит, что значение взято из записи KB-001.

`provenance` тоже считает сервер по источнику, а не по слову модели. Значение, которое агент вывел из описания, а не прочитал, получает `provenance: assumption`, `verified: false` и `mandatory: false`: подбор его учитывает и показывает как допущение, подбор оно не блокирует. Второму этапу нужно брать только `value`.

### Ключи требований

Если требование означает свойство из словаря [knowledge/requirement_keys.json](../knowledge/requirement_keys.json) (версия 2, 33 кода с подсказками `hint`), его `key` равен коду словаря. Интерпретатор заполняет коды отдельным блоком, а сервер приводит значение к виду, который читает второй этап: у числа диапазон источника остаётся диапазоном и без единицы получает единицу словаря, у флага «да» или «нет», у выбора и перечня с `options` только значения из `options`. Значение, которое так не читается, в требования не попадает и уходит в `unknowns`.

Код встречается в карточке один раз и заменяет свободный ключ: свободное требование с ключом заполненного кода отбрасывается, а с тем же смыслом под другим ключом его убирает проверяющий. Остальные требования получают собственный стабильный `key` в snake_case; второй этап их не учитывает и сообщает об этом.

### Вопросы

Вопросы задаёт проверяющий, все сразу. `kind` бывает `clarify` или `discrepancy` (расхождение источников, ТЗ и STL, требование против возможностей, дефект против назначения); `units`, `purpose` и `verify` остались у карточек прошлых версий. Пока вопросы открыты, они блокируют подбор. После ответа, даже «Не знаю», вопрос получает `blocking: false`: вместо неизвестного проверяющий делает допущение, и карточка уходит на подбор как `preliminary`.

## Разделение модели и сервера

Агенты возвращают черновики по своим схемам, ID источников в них короткие (`m1`, `f1p2`). Всё, что влияет на готовность, сервер считает сам: происхождение и подтверждённость требований, методы источников, вид значений кодов, гейты, `readiness`, ревизию, версии, `stl_analysis`. Поля, которые модель вернула сверх схемы, отбрасываются.
