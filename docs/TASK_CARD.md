# Карточка задания 2.0, контракт этапа 1 и этапа 2

Карточка `TaskCard` версии **2.0** это единственный результат первого этапа. Машиночитаемая схема лежит в [task-card-v2.0.schema.json](task-card-v2.0.schema.json), тест `tests/backend/test_schema.py` следит, чтобы она совпадала с кодом.

## Как второй этап получает карточку

Когда у карточки нет блокеров, первый этап в одной транзакции сохраняет её, переводит задание в `queued` на этап `parameters` и ставит задачу Procrastinate:

```
task: stage2.select_parameters   queue: stage2   lock: job:<job_id>
args: {"job_id": "...", "revision": 7}
```

Обработчик (`src/backend/pipeline/parameters.py`) берёт карточку текущей ревизии и проходит подбор параметров и его проверку. Как это устроено, описано в [PIPELINE.md](PIPELINE.md). Если пользователь успел изменить задание, новая ревизия отменяет ждущие задачи старой, а уже идущий шаг старой ревизии останавливается на охране ревизии. Карточка доступна по `GET /api/v1/jobs/{id}/card`.

## Поля

| Поле | Содержание |
| --- | --- |
| `schema_version`, `job_id`, `revision` | версия контракта и ревизия задания |
| `purpose` | назначение детали |
| `requirements[]` | требования: `key`, `label`, `value`, `unit`, `conditions`, `mandatory`, `provenance`, `sources[]`, `verified`, `superseded[]` |
| `preferences[]`, `production_constraints[]` | пожелания и ограничения производства |
| `assumptions[]` | допущения: `text`, `basis`, `consequence`; это не требования |
| `unknowns[]` | что неизвестно |
| `questions[]` | все вопросы с ответами пользователя |
| `geometry` | сводка анализа STL (габариты, дефекты, объём только когда он достоверен) |
| `stl_analysis` | полный отчёт анализатора активного STL без сокращений, `attachment_id`, `sha256` |
| `verdict` | оценка судьи: `score`, `passed`, `reworked`, `remarks[]` |
| `readiness` | `ready`, `preliminary` (есть допущения, неизвестные или дефекты) или `blocked` |
| `allowed_actions`, `blocked_actions` | `select_parameters` и причины блокировки |
| `files[]`, `versions` | исходные файлы с sha256; версии правил, анализатора, модели и каждого промпта |

### Источники требований

`sources[].source_id` это стабильная ссылка: `<attachment_id>:<страница>` для файлов, id сообщения для чата, `answer:<question_id>` для ответа, `kb:<record>` для базы знаний. Поле `method` устанавливает сервер:

- `text` значит, что цитата найдена в тексте документа дословно;
- `vision` значит, что значение прочитано с изображения и подтверждено независимым вторым чтением;
- `user` значит, что значение пришло из сообщения или ответа пользователя;
- `knowledge` значит, что значение взято из записи KB-001.

`verified: true` бывает только у требований с проверенными источниками. `superseded[]` хранит прежние значения с причиной: «Заменено сообщением пользователя» или «Отклонено решением пользователя». Второму этапу нужно брать только `value`.

### Ключи требований

Если требование означает свойство из словаря [knowledge/requirement_keys.json](../knowledge/requirement_keys.json), его `key` равен коду словаря. У числа тогда `unit` из словаря, диапазон источника остаётся диапазоном, и нужную границу выбирает второй этап по полю `strict` словаря; у флага `value` «да» или «нет», у выбора один из `options`, у перечня значения через запятую. Остальные требования получают собственный стабильный `key` в snake_case; второй этап их не учитывает и сообщает об этом. Число под кодом без единицы или в единице другой физической природы получает `verified: false` и вопрос `verify`.

### Вопросы

`kind` принимает значения `units`, `purpose`, `clarify`, `verify` (подтверждение значения) и `discrepancy` (расхождение источников, ТЗ и STL, требование против возможностей, дефект против назначения). Вопрос с `blocking: true` без ответа блокирует подбор параметров. Ответ «Не знаю» ответом не считается. Предложенный вариант (`suggested`) без выбора пользователя тоже не считается ответом.

## Разделение модели и сервера

Агенты возвращают черновики по своим схемам, ID источников в них короткие (`m1`, `f1p2`). Всё, что влияет на готовность, сервер считает сам: подтверждённость требований, методы источников, сведение значений, вопросы о единицах и назначении, гейты, `readiness`, ревизию, версии, `stl_analysis`. Поля, которые модель вернула сверх схемы, отбрасываются.
