# Принятые решения этапа 2

Формат: что решили · почему · чем заменить.

## Окружение и запуск
- **Пакет устанавливается через uv.** В `pyproject.toml` добавлен `build-system` (`uv_build`, `module-name = "tuning"`), поэтому `uv run python -m tuning select ...` работает без `PYTHONPATH`; JSON-данные входят в колесо (проверено `uv build --wheel`). Dev-инструменты: pytest, ruff (E, F, I, W, B; строка 120; `research/` исключён), mypy (типы — комментариями `# type:`, `from typing import Any  # noqa: F401` нужен только для них).
- **Каталог материалов не лежит в репозитории.** Путь передаётся `--materials-dir` или `STE_MATERIALS_DIR` (в слайсере — `resources/materials`). Файлы дистрибутива не копируем. E2E используют маленькие синтетические файлы.
- **Тяжёлые данные и карточки 7 деталей — в `.scratch/`.** Карточки собраны вручную по структурированным записям, абзацы ТЗ не копировались.

## Режимы 5D (проверено по коду `STE-Slicer` 3c863ed)
- `classic` и `cylindrical_full` в `CuraEngineBackend/StartSliceJob.py` читают значения `*_classic` (скорости, вентилятор, `support_enable`). `cylindrical` идёт через `CLIParserBackend`/glicer и читает `*_cylindrical`. Пакет `CylindricalBackend` объявляет тип `cylindrical_full`.
- **Допущение:** `cylindrical_full` выдаёт оба набора ключей (`*_classic` и `*_cylindrical`). Гипотеза, confidence не подтверждён кодом; нужен эксперт организаторов (вопрос 5).
- Высота области: 300 мм в `classic`, 250 мм в обоих 5D-режимах (из `steprinter530_v5.2`). Ориентация пока берётся как в STL.

## Пространство поиска
- Ищем 6 параметров: высота слоя, периметры, толщина оболочки (даёт `top_layers`/`bottom_layers`), плотность заполнения, температура сопла, скорость. Вентилятор и температуру стола берём из файла материала, а не ищем: направление влияния охлаждения зависит от материала и не монотонно.
- Ключи: `classic_layer_height`/`cylindrical_layer_height` — «листья» `layer_height`, их `value` равно `layer_height`, поэтому задаём их явно по режиму. `wall_line_count`, `top_layers`, `bottom_layers` в определении считаются формулами от толщин; мы задаём их явно и сами пересчитываем слои от толщины оболочки и высоты слоя. Явное значение перекрывает формулу.
- Скорость: ищем `speed_print`; `speed_wall_0_*`, `speed_infill_*` и т. д. считаются от неё формулами определения.
- Окно температуры: номинал из файла материала ±10 °C (в файле только одно значение), верхняя граница 285 °C (`maximum_value_warning` определения). Замена: окна из паспортов производителя.
- Скорость материала без значения: 50 мм/с (`DEFAULT_SPEED_MM_S`).
- Ось t: 0 — быстро/дёшево/хрупко, 1 — медленно/дорого/прочно. Слой: 0.32 (0.8·сопло) → 0.10 мм. Слои оболочки не меньше 3.
- Порог поддержек: доля площади нависаний > 0.05. Это оценка, не калибровка; на реальных деталях порог срабатывает почти везде (доли 0.08–0.15 при ориентации «как в STL»).
- Не проверено: в примерах деталей ось Z, по-видимому, не совпадает с осью печати (у части моделей короткий размер по Y). Поиск ориентации — P2.

## Материалы
- Пул подбора: файлы `enduse_*`, `fiberpart_*`, `sealant_*`. `generic_*` (Ultimaker, без скорости) и `contifiber`/`metalcast`/`proto` не ранжируем: нужны другая печатающая головка или они вспомогательные. Материал из карточки находим по всему каталогу.
- Свойства полимеров (Tg, температура эксплуатации, гигроскопичность, УФ, жёсткость и др.) в `catalog/traits.json` — **общие знания, не проверено** по паспортам; флаг `verified: false`. Плотность, температуры и описание берём из файлов каталога.
- Статус трёхзначный: `ok`, `warn`, `fail`, `unknown`. Жёсткое требование нарушает только `fail`; `unknown` попадает в `assumptions_used` как «не проверено».
- Конфликты: материал не найден для одного жёсткого требования → `unsatisfied` и `infeasible`; пара требований, которую не выполняет ни один материал одновременно, тоже `infeasible` с обоими `id`.
- Статус `infeasible` ставится только при доказанной несовместимости внутри наших моделей. «Поддержки запрещены, но есть нависания» остаётся в `unsatisfied` со статусом `proposed`: решается ориентацией, которую мы пока не ищем.

## Правила режима
- По умолчанию `classic` (вес 1). Единственное правило в пользу 5D: запрет поддержек + нависания (вес 2, confidence 0.35, гипотеза). Остальное — подсказка карточки `preferences.printing_mode` (вес 10). Режим, в который деталь не помещается, исключается.

## Состояние и детерминизм
- `new_state` — JSON-словарь (`tuning_state/0`). Все выходы через `json.dumps(sort_keys=True, ensure_ascii=False)`. Генераторов случайных чисел в M0 нет; сид записывается в состояние.

## Вход от этапа 1 (карточка v1.1)
- **Адаптер на границе, ядро не меняется.** `tuning.intake` переводит `{idempotency_key, card}` во внутренние `task_card/0` и `geometry/0`. Путь `--card/--stl` остаётся: на нём работают стенд экспериментов и E2E F-TUNE-1…5. Замена: убрать этот путь, когда эксперименты перейдут на карточки этапа 1.
- **Коды требований сопоставляются по данным** (`intake/vocabulary.json`), а не по коду. Этап 1 выдаёт свободные коды (`load_bearing`, `surface_finish`…), и угадывать их смысл в коде нельзя. Неизвестное обязательное требование не теряется: оно попадает в `assumptions_used` как «не используется подбором».
- **Диапазон даёт строгую границу.** Для порогов «не ниже» (Tg, температура эксплуатации) берём верхнюю границу, для «не выше» (плотность, допуск) — нижнюю. «Tg ≥ 85–90» превращается в 90. Замена: передавать диапазон в правила целиком.
- **Минус — знак только в начале слова.** «85-90» — это диапазон, «-10..70» начинается ниже нуля. Число без единицы или с чужой единицей не принимается: иначе «70» без `°C` молча стало бы температурой.
- **Подтверждённость.** `verified: false` или `provenance: assumption` → `source: assumption`. Материал из такого требования не используется, вместо него ранжируем каталог.
- **Свободный текст `preferences` / `production_constraints`.** Из него извлекаются только приоритеты, запрет поддержек и нагрузка, по фразам из словаря. Каждый такой вывод записывается в `assumptions_used`.
- **Готовность.** Подбор отказывает, если `readiness = blocked` или в `blocked_actions` есть `select_parameters`: этап 1 явно говорит, что подбирать рано. `preliminary` разрешён, оговорка идёт первой строкой в `assumptions_used`.
- **Единицы.** Сервер этапа 1 сам пересчитывает координаты в мм, когда единицы подтверждены (`coordinate_unit: mm`). При `unknown` принимаем мм и пишем это допущение в каждый ответ.
- **Нависаний в отчёте нет.** Факт `geometry.overhang_area_fraction` не задаётся, поэтому правила поддержек и 5D по нависаниям не срабатывают, поддержки остаются выключенными. Это допущение пишется в ответ. Считать нависания самим нельзя: STL этапу 2 не передаётся. Запрос к этапу 1 — в INTEGRATION.md.
- **Тонкая стенка** — `normal_chords.minimum_sampled` из отчёта (выборочная хорда, оценка) вместо `2V/A`.
- **`idempotency_key`** копируется в ответ и состояние. Вызов цикла с состоянием другой ревизии отклоняется: на старое состояние нельзя применять новую карточку.
