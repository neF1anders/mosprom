# Принятые решения этапа 2

Формат: что решили · почему · чем заменить.

## Окружение и запуск
- **Пакет устанавливается через uv.** Сборщик `uv_build`, пакет `tuning`, `uv run python -m tuning select ...`, JSON-данные входят в колесо. Dev-инструменты: pytest, ruff, mypy; типы — комментариями `# type:` (код совместим с Python 3.5).
- **Каталог материалов не лежит в репозитории.** Путь — `--materials-dir` / `STE_MATERIALS_DIR` (в слайсере — `resources/materials`). E2E используют синтетические файлы.
- **Проверка этапа 3 и ресурсы сборки не копируются.** Они в ветке `fedor/validation-ste`. Тест `test_stage3_checker.py` запускает их при заданной `VALIDATION_DIR`, сверку наших данных с ресурсами сборки — при `STE_RESOURCES_DIR`, иначе тесты пропускаются.

## Контракты
- **Выход — `stage2.parameter_set` v0.1 этапа 3, свой формат `param_set/0` удалён.** Этап 3, адаптер и чат читают один JSON. Наши поля сверх контракта (`status`, `unsatisfied`, `warnings`, `idempotency_key`, альтернативы материала, `orientation_candidate`) предложены этапу 3: проверка лишние поля не ругает.
- **Цикл `verdict/0`, стратегии M0–M5, стенд экспериментов и чтение STL удалены.** По новому протоколу заходов не больше двух, а вместо сигналов `too_weak`/`too_costly` приходят ограничения `eq/ne/min/max/in`. Ограничение — это готовая граница, бисекция не нужна. STL этапу 2 больше не передаётся. Код прежней версии — в git до `be7c18b`. Замена: если этап 3 вернётся к сигналам, стратегию можно восстановить поверх `planning.py`.
- **Без состояния.** Заход 2 пересчитывается из карточки и обратной связи, результат детерминирован.

## Принтер и профиль качества (выданная сборка 5.2.4)
- **Принтер — `hte530v5.2.4`.** Данные в `space/profile.hte530v5.2.4.json`, тест сверки с ресурсами сборки:
  - стол 351 × 300,3 мм; высота 300 мм в 3D, 231,1 мм в 5D;
  - в 5D стол эллиптический, без подогрева;
  - запретные полосы в 3D оставляют по X рабочую область [−169,5; 150,5];
  - адгезия по умолчанию в `cylindrical_full` — `raft`.

  Прежние 315 / 250 мм были из GitHub-версии `hte530v5.2`.
- **Слой выбирается профилем качества, а не числом.** Правила дают целевой слой, он привязывается к ближайшему профилю в допустимых пределах: `high` 0,06, `normal` 0,1, `fast` 0,15, `draft` 0,2, `verydraft` 0,3. `coarse` и `extra coarse` толще 0,8 сопла. `layer_height` отправляется, только если ни один профиль не укладывается в пределы. Почему: жюри сравнивает профиль, а слой вроде 0,17 не совпадёт ни с каким эталоном.
- **Профиль по умолчанию — `normal` (Fine 0,1 мм).** Это `preferred_quality_type` в `fdmprinter`. Профили «Fine» стоят и в тестовых G-code Stereotech. Правило «не тоньше 0,1 мм» (S 4.2) оставлено, поэтому `high` (0,06) сейчас недостижим. Замена: снять правило, если эталоны жюри окажутся на 0,06.
- **Положение модели.** Центр рабочей области стола (в 3D x = −9,5, в 5D — ось вращения 0, 0), высота центра — половина высоты модели, поворот «как загружено». Подбор ориентации невозможен, пока этап 1 не передаёт нависания по направлениям.

## Старт от значений слайсера
- **Каждая ось стартует от значения, которое слайсер взял бы сам.** Профиль качества (у `fast` — `wall_thickness` 1 мм и заполнение 10 %), файл материала (температура) или определение (`wall_thickness` 0,8, кожа 0,8, заполнение 20 %, скорость 60). Затем старт приводится в жёсткие пределы, сдвигается правилами и снова приводится в пределы. Отправляется только то, что отличается от старта. Почему: контракт этапа 3 — «только отличия», а прежний старт с середины оси (t = 0,5) выдавал 4 периметра и 35 %, которых нет ни в профиле, ни в требованиях.
- **Сдвиги правил считаются от старта, уже приведённого в пределы.** Пример: «жёсткость обязательна» (минимум 4 периметра) плюс «прочность» дают 5. Ограничение этапа 3 «минимум 5» вместе с приоритетом прочности даёт 6: значение законно, ограничение выполнено.
- **Периметры отправляются толщиной.** Отправляем `wall_thickness = n · 0,4`. Формула слайсера `round((t − 0,4) / 0,4) + 1` возвращает ровно n (проверено тестом для 2–6). Профиль `fast` с 1 мм по той же формуле даёт 2 линии (1,4999… округляется вниз).
- **Кожа отправляется как `top_bottom_thickness`, не числом слоёв.** Не меньше 3 слоёв: если толщина меньше 3 · слой, она поднимается.
- **Скорость.** Старт — 60 мм/с слайсера. Скорость из файла материала (`speed print`) слайсер не применяет: в `XmlMaterialProfile` у неё нет сопоставления. Поэтому она работает как верхний предел (`SPEED-MATERIAL-MAX`) и обычно попадает в выход.
- **Температура.** Окно ±10 °C от файла материала. Предел принтера 285 °C (`maximum_value_warning`) не опускает материал ниже его собственного значения: у `fiberpart_pc_g20` в файле 290 °C.
- **Обдув.** Если в файле материала обдув 0 %, отправляем `cool_fan_enabled_<режим> = false`. Так печатаются такие материалы в тестовых G-code Stereotech, и обдув становится явным. Ключ режима: у `cool_fan_enabled` ключи `_classic` / `_cylindrical` не связаны формулой с общим. В `cylindrical_full` отправляется только `_cylindrical`, иначе проверка этапа 3 предупреждает (открытый вопрос этапу 3).
- **Решаем, но обычно не отправляем.** Температура стола и скорость обдува берутся из материала. В 5D температура стола не отправляется никогда: стол не греется. `support_type`, `support_angle`, `retraction_enable` и 5D-ключи (диаметр основания, плот, `cylindrical_layer_height_0`) остаются значениями слайсера, пока нет данных (нависания, отверстие). `cylindrical_layer_height`, `support_enable_cylindrical`, `cylindrical_raft_thickness` и `cylindrical_raft_diameter` — формулы от исходных ключей.

## Материалы
- **Только пруток экструдера (1,75 мм).** `read_materials` пропускает файлы с другим диаметром. Раньше «PLA» находился как `generic_pla` (2,85 мм), которого нет в слайсере для этого принтера.
- **Пул ранжирования:** `enduse_*`, `fiberpart_*`, `sealant_*`, `generic_*` (1,75 мм), кроме растворимой поддержки PVA. Свойства полимеров (`catalog/traits.json`) — общие знания, `verified: false`. Для `generic_*_175` они добавлены, чтобы материал без данных не маскировал конфликт требований.
- **Частично выполненное обязательное требование (`warn`) и непроверенное (`unknown`)** попадают в `assumptions`, а не только в `checks`.
- **Химстойкость на русском** («щёлочи») сопоставляется с кодом по основам слов из `traits.json`.

## Вход от этапа 1 (карточка v1.1)
- **Адаптер на границе.** `tuning.intake` переводит карточку во внутренние `task_card/0` и `geometry/0`, `card_ref` берётся из `idempotency_key` (`job_id:revision`) или `source_versions`.
- **Коды требований сопоставляются по данным** (`intake/vocabulary.json`). Неизвестное обязательное требование пишется в `assumptions` («не учтено подбором»). Повтор кода получает id `key-2`: `#` не проходит шаблон `source` этапа 3.
- **Диапазон даёт строгую границу:** верхнюю для «не ниже» (Tg, температура эксплуатации), нижнюю для «не выше» (плотность, допуск). Минус считается знаком только в начале слова. Число без единицы или с чужой единицей не принимается.
- **Подтверждённость.** `verified: false` или `provenance: assumption` → `source: assumption`. Материал из такого требования не используется.
- **Свободный текст.** Из `preferences` / `production_constraints` берутся только приоритеты, запрет поддержек и нагрузка, по фразам словаря. Каждый вывод записывается в допущения.
- **Готовность.** Отказ при `readiness = blocked` или `select_parameters` в `blocked_actions`. `preliminary` разрешён с оговоркой.
- **Единицы.** При `coordinate_unit: unknown` координаты принимаются за мм, это допущение в каждом ответе.

## Обратная связь этапа 3
- **Ограничения на оси — жёсткие границы** (`limit_param`). Противоречие обязательному требованию даёт `infeasible` с парой (`high_stiffness` ↔ `constraint:C1`). `ne`/`in` на оси не поддержаны.
- **Ограничения на выбор** (режим, профиль, материал) проверяются по итоговому результату. Если результат им не соответствует (деталь не помещается, материала нет в каталоге), ставится `not_applied` и пишется в `unsatisfied`. Ничего не объявляется применённым без проверки.
- **Ключи, которые этап 2 не моделирует,** передаются как есть с `source: constraint:<id>`. Для `min`/`max` передаётся сама граница. `ne` без модели настройки выполнить нельзя, ставится `not_applied`.
- **Исключение ориентации.** Кандидат у нас один (`o1`). Если этап 3 его исключил, это попадает в `unsatisfied`.

## Режим печати
- По умолчанию `classic` (вес 1). Требование `printing_mode` карточки — вес 10, ограничение этапа 3 — вес 1000. Гипотеза «нависания + запрет поддержек → 5D Spiral» — вес 2. Режим, в который деталь не помещается (с учётом эллиптического стола 5D), исключается. Это пишется в допущения, если о режиме просили.
- Если деталь не помещается в выбранный режим, ставится `infeasible`, а в `unsatisfied` перечисляются режимы, куда она поместилась бы.
