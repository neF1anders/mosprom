# Принятые решения этапа 2

Формат: что решили · почему · чем заменить.

## Код и запуск
- **Ядро этапа 2 — пакет `src/backend/tuning` на Python 3.11.** Публичный вызов один: `select_parameters(card, catalog, keys, feedback=None)` в `select.py`. Его вызывает конвейер в воркере, своего CLI и чтения переменных окружения нет. Код перенесён из ветки `feat/parameters_tuning` (автор ne-F1anders) с сохранением истории: логика подбора авторская, поменялась форма.
  - Между модулями ходят неизменяемые dataclass, на границах pydantic: `TaskCard`, `Feedback`, `ParameterSet` из `src/backend/domain`.
  - Решения идут цепочкой чистых функций (`select.py`): материал → режим → план правил и ограничений → профиль → настройки → модель. Каждая возвращает результат с причинами.
  - Ошибки входа — `AppError` с кодом, пользователь видит понятную причину.
- **Данные остаются JSON рядом с кодом:** `rules.json`, `search_space.json`, `traits.json`, `phrases.json`, `printer.json`. Их проверяет pydantic при импорте, ошибка в данных роняет старт воркера, а не задачу пользователя.
- **Каталог сборки один на этапы 2 и 3.** `knowledge/ste_5.2.4` читает `infrastructure/catalog.py`, этап 2 получает готовый `Catalog`.
- **Тесты** — `tests/backend/tuning` (маркер `unit`), с настоящим каталогом сборки, без пропусков. Эталоны исходного кода — `tests/fixtures/tuning`, побайтовая сверка — `test_golden.py`.

Цикл `verdict/0` и стратегии M0–M5 удалены ещё у автора (в git до `be7c18b`).
- **Без состояния.** Заход 2 пересчитывается из карточки и обратной связи, результат детерминирован побайтово.

## Принтер и профиль качества (выданная сборка 5.2.4)
- **Принтер — `hte530v5.2.4`, данные берутся из каталога сборки** (`printer.py`), а не из ручного профиля:
  - стол 351 × 300,3 мм (`machine_width`, `machine_depth`); высота 300 мм в 3D, 231,1 мм в 5D (формула `machine_height`);
  - в 5D стол эллиптический (`machine_shape`), без подогрева (`machine_heated_bed`);
  - запретные полосы `machine_disallowed_areas` в 3D оставляют по X рабочую область [−169,5; 150,5];
  - сопло 0,4 и пруток 1,75 мм — из экструдера 0, ширина линии 0,4 — формула `line_width`;
  - предел температуры 285 °C — `maximum_value_warning` у `material_print_temperature`;
  - адгезия режима — формула `adhesion_type` (`raft` в `cylindrical_full`), рисунок заполнения — формула `infill_pattern` по выбранной плотности;
  - слои профилей и значения профиля `fast` (`wall_thickness` 1 мм, заполнение 10 %) — файлы `quality`; профиль без слоя печатает слоем сборки 0,1 мм.

  Значение берётся так, как его взял бы слайсер: выбранное подбором, иначе из профиля качества, экструдера, принтера, иначе формула или значение `fdmprinter`.
- **Из каталога не выводится только профиль по умолчанию** `normal`: это `preferred_quality_type` в метаданных `fdmprinter`, а каталог метаданные не хранит. Он лежит в `printer.json`, тест сверяет его со сборкой. Замена: перенести метаданные в `Catalog`.
- **Ключи вентилятора по режиму** (`cool_fan_enabled_classic` / `_cylindrical`) формулой с общим ключом не связаны, поэтому заданы в `search_space.json` (`mode_keys`). Тест проверяет, что такие ключи есть в сборке.
- **Слой выбирается профилем качества, а не числом.** Правила дают целевой слой, он привязывается к ближайшему профилю в допустимых пределах: `high` 0,06, `normal` 0,1, `fast` 0,15, `draft` 0,2, `verydraft` 0,3. `coarse` и `extra coarse` толще 0,8 сопла. `layer_height` отправляется, только если ни один профиль не укладывается в пределы. Почему: жюри сравнивает профиль, а слой вроде 0,17 не совпадёт ни с каким эталоном.
- **Профиль по умолчанию — `normal` (Fine 0,1 мм).** Профили «Fine» стоят и в тестовых G-code Stereotech. Правило «не тоньше 0,1 мм» (S 4.2) оставлено, поэтому `high` (0,06) сейчас недостижим. Замена: снять правило, если эталоны жюри окажутся на 0,06.
- **Положение модели.** Центр рабочей области стола (в 3D x = −9,5, в 5D — ось вращения 0, 0), высота центра — половина высоты модели, поворот «как загружено». Ориентация пока не подбирается. Доля нависаний из отчёта STL относится к модели как в файле, кандидаты `orientations` ещё не читаются.

## Старт от значений слайсера
- **Каждая ось стартует от значения, которое слайсер взял бы сам.** Профиль качества, файл материала (температура) или сборка (`wall_thickness` 0,8, кожа 0,8, заполнение 20 %, скорость 60). Затем старт приводится в жёсткие пределы, сдвигается правилами и снова приводится в пределы. Отправляется только то, что отличается от старта. Почему: контракт этапа 3 — «только отличия», а старт с середины оси (t = 0,5) выдавал бы 4 периметра и 35 %, которых нет ни в профиле, ни в требованиях.
- **Сдвиги правил считаются от старта, уже приведённого в пределы.** Пример: «жёсткость обязательна» (минимум 4 периметра) плюс «прочность» дают 5. Ограничение этапа 3 «минимум 5» вместе с приоритетом прочности даёт 6: значение законно, ограничение выполнено.
- **Периметры отправляются толщиной.** Отправляем `wall_thickness = n · 0,4`. Формула слайсера `round((t − 0,4) / 0,4) + 1` возвращает ровно n (проверено тестом для 2–6). Профиль `fast` с 1 мм по той же формуле даёт 2 линии (1,4999… округляется вниз).
- **Кожа отправляется как `top_bottom_thickness`, не числом слоёв.** Не меньше 3 слоёв: если толщина меньше 3 · слой, она поднимается.
- **Скорость.** Старт — 60 мм/с сборки. Скорость из файла материала (`speed print`) слайсер не применяет: в `XmlMaterialProfile` у неё нет сопоставления. Поэтому она работает как верхний предел (`SPEED-MATERIAL-MAX`) и обычно попадает в выход.
- **Температура.** Окно ±10 °C от файла материала. Предел принтера 285 °C (`maximum_value_warning`) не опускает материал ниже его собственного значения: у `fiberpart_pc_g20` в файле 290 °C.
- **Обдув.** Если в файле материала обдув 0 %, отправляем `cool_fan_enabled_<режим> = false`. Так печатаются такие материалы в тестовых G-code Stereotech, и обдув становится явным. В `cylindrical_full` отправляется только `_cylindrical`, иначе проверка этапа 3 предупреждает (открытый вопрос этапу 3).
- **Решаем, но обычно не отправляем.** Температура стола и скорость обдува берутся из материала. В 5D температура стола не отправляется никогда: стол не греется. `support_type`, `support_angle`, `retraction_enable` и 5D-ключи (плот, `cylindrical_layer_height_0`) остаются значениями сборки. Диаметр основания 5D отправляется, когда отчёт STL передал отверстие детали от 4 мм. `cylindrical_layer_height`, `support_enable_cylindrical`, `cylindrical_raft_thickness` и `cylindrical_raft_diameter` — формулы от исходных ключей.

## Материалы
- **Материалы — `Catalog.materials`, только пруток экструдера (1,75 мм).** Файлы с другим диаметром пропускаются: «PLA» не должен находиться как `generic_pla` (2,85 мм), которого нет в слайсере для этого принтера.
- **Файл без температуры печати пропускается с предупреждением.** Без неё нет окна температур, исходный код падал на таком файле. Если такой материал назван в карточке, ответе или ограничении, подбор останавливается ошибкой `material_without_temperature`: молча подменить названный материал нельзя.
- **Пул ранжирования:** `enduse_*`, `fiberpart_*`, `sealant_*`, `generic_*` (1,75 мм), кроме растворимой поддержки PVA. Свойства полимеров (`traits.json`) — общие знания, `verified: false`. Для `generic_*_175` они добавлены, чтобы материал без данных не маскировал конфликт требований.
- **Частично выполненное обязательное требование (`warn`) и непроверенное (`unknown`)** попадают в `assumptions`, а не только в `checks`.
- **Химстойкость на русском** («щёлочи») сопоставляется с кодом по основам слов из `traits.json`.

## Вход от этапа 1 (карточка 2.0)
- **Адаптер на границе.** `intake.py` читает `TaskCard` в типизированный `TuningInput`: `job_id` и `revision` из карточки, допущения объектами, ответы из `questions[].answer`, геометрия из `stl_analysis.report` (`geometry.py`).
- **Коды требований и единицы — общий словарь** `knowledge/requirement_keys.json` (код, вид, единица, строгий конец диапазона) и `domain/units.py`. Синонимов на стороне этапа 2 нет: прежний псевдоним `service_temperature` удалён, этап 1 пишет `service_temp_max_c`. Неизвестное обязательное требование пишется в `assumptions` («не учтено подбором»). Повтор кода получает id `key-2`: `#` не проходит шаблон `source` этапа 3.
- **Диапазон даёт строгую границу** из словаря: верхнюю для «не ниже» (Tg, температура эксплуатации), нижнюю для «не выше» (плотность, допуск). Число в другой единице той же величины переводится в единицу кода (0,01 см → 0,1 мм, К → °C). Число без единицы или с единицей другой величины не принимается.
- **Подтверждённость.** `verified: false` или `provenance: assumption` → требование-допущение. Материал из такого требования не используется.
- **Нагрузка и режим.** Код словаря (`cyclic`, `cylindrical_full`) берётся как есть. Нагрузку, написанную текстом, распознают фразы `phrases.json`, это допущение.
- **Свободный текст.** Из `preferences` и `production_constraints` берутся только запрет поддержек, нагрузка и приоритеты, по фразам `phrases.json`. Каждый вывод записывается в допущения.
- **Приоритеты кодом.** Код `priority` карточки важнее текста пожеланий: берутся только `strength`, `accuracy`, `speed`, `cost` в указанном порядке, остальное уходит в предупреждения. Код не даёт факта `req.priority`, правила читают `pref.priority_first`. Неподтверждённый код пишется в допущения.
- **Коды выбора** (`part_class`) берутся, только если значение есть в `options` словаря. Иначе требование «не учтено». `load_bearing` и `printing_mode` читаются своими полями.
- **Новые разделы отчёта STL.** `overhangs.area_fraction` даёт факт `geometry.overhang_area_fraction`, `revolution.bore.diameter_mm` даёт диаметр основания 5D. Без них выход прежний, байт в байт.
- **Готовность.** Отказ при `readiness = blocked` или `select_parameters` в `blocked_actions`. `preliminary` разрешён с оговоркой.
- **Единицы STL.** При `coordinate_unit: unknown` координаты принимаются за мм, это допущение в каждом ответе.

## Обратная связь этапа 3
- **Ограничения на оси — жёсткие границы** (`limit_axis`). Противоречие обязательному требованию даёт `infeasible` с парой (`high_stiffness` ↔ `constraint:C1`). Граница за пределами оси даёт `infeasible` с одним ограничением (исходный код здесь падал). `ne`/`in` на оси не поддержаны.
- **Ограничения на выбор** (режим, профиль, материал) проверяются по итоговому результату. Если результат им не соответствует (деталь не помещается, материала нет в каталоге), ставится `not_applied` и пишется в `unsatisfied`. Ничего не объявляется применённым без проверки. `material eq` с материалом каталога даёт `source: constraint:<id>` (исходный код здесь падал).
- **Ключи, которые этап 2 не моделирует,** передаются как есть с `source: constraint:<id>`. Для `min`/`max` передаётся сама граница, для `in` — первое значение. `ne` и пустой `in` без модели настройки выполнить нельзя, ставится `not_applied`.
- **Исключение ориентации.** Кандидат у нас один (`o1`). Если этап 3 его исключил, это попадает в `unsatisfied`.

## Режим печати
- По умолчанию `classic` (вес 1). Требование `printing_mode` карточки — вес 10, ограничение этапа 3 — вес 1000. Гипотеза «нависания + запрет поддержек → 5D Spiral» — вес 2. Режим, в который деталь не помещается (с учётом эллиптического стола 5D), исключается. Это пишется в допущения, если о режиме просили.
- Если деталь не помещается в выбранный режим, ставится `infeasible`, а в `unsatisfied` перечисляются режимы, куда она поместилась бы.
