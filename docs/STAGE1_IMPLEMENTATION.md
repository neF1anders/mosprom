# Первый этап, реализация

Первый этап превращает сообщения пользователя, вложения и STL в единую карточку задания для второго этапа (подбора параметров). Архитектура согласована с пользователем 23–24 октября 2026 года. Поведение и ограничения проектирования описаны в [STAGE1_DESIGN.md](STAGE1_DESIGN.md), контракт карточки описан в [TASK_CARD.md](TASK_CARD.md).

## Запуск

Сервер работает локально у каждого пользователя. STE Slicer открывает встроенный браузер на `localhost` и заданном порту по одноразовой ссылке. Сейчас поставка идёт через Docker Compose, нативный установщик для Windows запланирован позже. Код не привязан к Linux: пути, порты и адрес базы задаются настройками.

```bash
python3 scripts/bootstrap.py            # создаёт .env с SESSION_SECRET
# в .env задайте QWEN_API_KEY
docker compose up --build -d            # db, api, worker; миграции и база знаний применяются при старте api
python3 scripts/bootstrap.py <user_id>  # печатает ссылку запуска для пользователя
```

Ссылка одноразовая и действует 10 минут. Плагин строит такую же ссылку тем же секретом и передаёт в ней `user_id`. После обмена браузер получает HttpOnly-cookie сессии с этим пользователем, и каждый пользователь видит только свои задания.

Миграции начинаются с новой базовой схемы `0001_baseline`. Базу, созданную до этой переделки, нужно пересоздать командой `docker compose down -v`.

## Как идёт прогон

Любое действие пользователя (сообщение, отправка файлов, ответ, повтор) в одной транзакции делает три вещи: создаёт новую ревизию задания, сохраняет событие и ставит задачу Procrastinate `stage1.run(job_id, revision)`. Исключение составляют ответы, данные после публикации первых вопросов (фаза `deep`): они сохраняются без новой ревизии, и текущий прогон читает их на шаге сводки. Новый STL заменяет прежний только при отправке, поэтому убранный до отправки файл не сбрасывает подтверждённые единицы. Воркер выполняет задачу так:

```
0 тема        если ревизию начало одно сообщение без новых файлов, быстрый вызов без рассуждений
              решает, относится ли оно к заданию; на приветствие и постороннюю тему агент коротко
              отвечает, карточка остаётся прежней, а сообщение больше не попадает к агентам
1 файлы       документы разбираются параллельно в отдельных процессах: текст, PNG страниц, рисунки
              из DOCX; файл, который не прочитался раньше, пробуется снова
2 одновременно стартуют
  STL                         анализатор строит отчёт, сводку и PNG проекций (кеш по sha256 и
                              единицам, отчёт, обрезанный таймаутом, не кешируется); вопрос о
                              единицах публикуется сразу, как только известны габариты
  быстрый разбор              один вызов без рассуждений, поля из domain/fields.py с цитатами;
                              по полям без цитаты от 2 до 5 вопросов, их видно через 10–20 секунд
  глубокий разбор             интерпретатор и разборщики нагрузок, среды, производства;
                              разборщик геометрии ждёт отчёт STL и единицы, остальные не ждут
3 сводящий                    правка черновика по id требований, ответы пользователя входят здесь
4 код                         применение правки, проверка цитат, второе чтение картинок
                              (страницы параллельно), сведение значений
5 несоответствия и судья      параллельно; ниже порога сводящий дорабатывает один раз
6 код                         гейты готовности, сборка карточки 2.0
```

Если единицы STL не подтверждены, шаг 2 всё равно выполняется, а прогон заканчивается вопросом о единицах. После ответа заново работают только разборщик геометрии и шаги 3–6, остальное берётся из кеша.

Результат каждого агента кешируется по промпту, модели, бюджету рассуждений и его собственному входу. Блоки входа сериализуются с сортировкой ключей, поэтому отчёт STL, прочитанный обратно из JSONB, даёт тот же ключ. Ответ, из которого проверка схемы выбросила элементы, не кешируется: следующий вызов может вернуть его целиком. Каждый агент получает только те блоки, от которых зависит: интерпретатор, быстрый разбор и разборщики не видят ответов и сводки STL, поэтому ответ не повторяет их работу. Новое сообщение или файл меняют вход и честно пересчитывают шаг 4. Вопрос о поле быстрого разбора получает постоянный id `field.<ключ>`, поэтому отвеченный вопрос не возвращается в другой формулировке.

Если блокеров нет, задание получает статус `queued` на этапе `parameters`, и в той же транзакции ставится задача `stage2.select_parameters`: дальше работают подбор параметров и его проверка ([PIPELINE.md](PIPELINE.md)). Если блокеры есть, задание получает статус `waiting_user`, а вопросы показываются в окне вопросов.

Каждые 2 секунды прогон проверяет, что ревизия актуальна и что не нажат «Стоп», и при необходимости прерывает даже вызов модели в полёте. Результат устаревшей ревизии не становится текущим. Весь прогон ограничен 15 минутами при целевых 5.

## Агенты

Каждый агент описывается промптом (`src/backend/agents/prompts/<имя>.md` плюс общие правила `common.md`), набором инструментов и схемой ответа. Все агенты работают через общий раннер `agents/runner.py`.

| Агент | Задача | Инструменты |
| --- | --- | --- |
| gate | относится ли последнее сообщение к заданию; короткий ответ на приветствие и постороннюю тему; без рассуждений | нет |
| triage | какие поля из `domain/fields.py` есть в данных, с цитатами, и название чата; без рассуждений | нет |
| interpreter | черновик карточки по сообщениям и документам, ключи по словарю кодов | view_page, convert_units |
| analyst_loads, analyst_environment, analyst_production, analyst_geometry | независимое прочтение требований своего аспекта, без черновика; ключи по словарю кодов; у производства в запросе вся база знаний, у геометрии сводка, полный отчёт STL и проекции | view_page, convert_units |
| consolidator | правка черновика по id требований: добавить, исправить, убрать, привести ключ к коду словаря; вопросы без повторов | view_page, convert_units |
| second_reading | независимое чтение значений со страницы, без чужих ответов | нет |
| discrepancies | несоответствия трёх видов для пользователя; отчёт STL и база знаний уже в запросе | view_page, convert_units |
| judge | оценка итоговой карточки с чистым контекстом | view_page |

Сервер при старте один раз превращает словарь кодов требований `knowledge/requirement_keys.json` в блок `requirement_keys` (код, вид, название, единица или варианты). Его получают только агенты, которые пишут требования: интерпретатор, разборщики и сводящий. Требование, которое означает свойство из словаря, получает его код: число в единице словаря (диапазон остаётся диапазоном), флаг «да» или «нет», выбор из вариантов. Остальные требования сохраняют собственный ключ. `convert_units` нужен только когда единица источника отличается от единицы словаря.

Бюджеты рассуждений (`thinking_budget`) стоят около 90-го процентиля по трассировке: 9000 у интерпретатора и сводящего, 8000 у разборщиков, 6000 у судьи, 4000 у поиска несоответствий и второго чтения. Они срезают только длинные хвосты.

Модель вызывается потоком. Таймаут 120 секунд означает тишину: нет первого токена или паузы между токенами. Общий предел на вызов 10 минут. Повтор делается только при сбое соединения, ответах 429 и 5xx или оборванном потоке, каждый повтор пишется в лог воркера.

Инструменты только читают данные. `view_page` показывает страницу или её область крупнее, `convert_units` точно переводит единицы одной физической природы. Отчёт STL и вся база KB-001 лежат прямо в запросе тех агентов, которым нужны, поэтому инструментов для их повторного чтения нет: каждый такой вызов стоил лишнего полного раунда модели. Анализ STL инструментом не является: его выполняет код.

## Гардрейлы

| Где | Что | Как |
| --- | --- | --- |
| Код | вход | типы и размеры файлов, 50 страниц на PDF, 150 страниц и изображений на задание, разбор в изолированном процессе с лимитами CPU и памяти |
| Код | инъекции | данные передаются в тегах с пометкой, что это не инструкции; документ не может закрыть тег; инструменты только читают; у каждого агента свой список инструментов; аргументы валидируются |
| Код | зацикливание | лимит шагов у каждого агента, последний шаг без инструментов, повтор того же вызова получает тот же результат, таймаут прогона |
| Код | JSON модели | только `json-repair` и поэлементная проверка, неверный элемент отбрасывается и пишется в журнал; обрезанный ответ считается ошибкой; модель никогда не просят исправить JSON |
| Код | цитаты | для текста, сообщений и записей базы цитата ищется дословно, числа значения должны быть в цитате как есть или после перевода из единицы, которую называет цитата, в единицу требования; допущение не может быть подтверждённым требованием |
| Код и модель | картинки | значение только с изображения подтверждается независимым вторым чтением страницы; при расхождении задаётся вопрос |
| Код | противоречия | значения сравниваются с учётом единиц; сообщение пользователя главнее документов, а новое сообщение главнее старого; расхождение документов уходит пользователю; выбор записывается в требование, прежнее значение остаётся в `superseded` |
| Код | коды требований | число под кодом словаря без единицы или в единице другой физической природы не подтверждается; по обязательному требованию задаётся вопрос `verify`, ответ числом без единицы получает единицу словаря |
| Код | геометрия | масштаб STL только из ответа пользователя, числа только из отчёта анализатора, отчёт проверяется по sha256 и единицам |
| Код | готовность | читаемый STL, подтверждённые обязательные требования, ответы на блокирующие вопросы, прочитанные файлы, пройденная итоговая проверка |
| Промпты | смысл | не выдумывать, цитировать дословно, сохранять условия, не смешивать номинал и пик, не путать кг и Н, брать код словаря только для того же свойства, не спрашивать то, что решает подбор параметров |
| Судья | точность и полнота | порог `JUDGE_THRESHOLD` (0.7), один круг доработки, при повторном провале карточка блокируется |

## Хранение, очередь, трассировка

PostgreSQL хранит задания (`user_id` и JSONB), сообщения, вложения, события, квитанции команд, кеш отчётов STL и результатов агентов, базу знаний KB-001, а также схему Procrastinate. У каждой таблицы свой репозиторий в `infrastructure/repositories.py`, сервисы и агенты обращаются к ним только через единицу работы и порты. Команды идемпотентны по `request_id`. Воркер (`python -m src.backend.worker`) каждые 30 секунд возвращает в очередь задачи воркеров, которые перестали присылать heartbeat. Проверки только при старте мало: задача, убитая этим же перезапуском, тогда ещё выглядит живой. Воркеров можно запускать несколько, а задачи одного задания выполняются последовательно благодаря lock `job:<id>`.

Таблица `agent_calls` хранит каждый вызов агента: запрос (картинки ссылками на файлы, а не base64), сырой ответ провайдера с `reasoning_content`, `finish_reason` и `usage`, вызовы инструментов с результатами, длительность и ошибку. Каждый шаг пишет только добавленные им сообщения и `offset` в диалоге, поэтому объём не растёт квадратично. Результат, взятый из кеша, тоже пишется строкой с `cached = true` и ключом кеша. Ошибки процессов разбора файлов попадают в лог воркера с хвостом stderr. Пользователь видит только краткие события в журнале.

```sql
SELECT agent, step, cached, duration_ms, response->'usage' FROM agent_calls WHERE job_id = '...' ORDER BY id;
```

## HTTP API

Префикс `/api/v1`. Изменяющие команды требуют UUID `request_id`.

- `POST /jobs`, `GET /jobs`, `GET /jobs/{id}` создают задание, отдают список с курсором и снимок задания.
- `POST /jobs/{id}/messages` принимает сообщение, это новая ревизия.
- `POST /jobs/{id}/attachments` и `POST /jobs/{id}/attachments/{attachment}/detach` добавляют и убирают файл. Отправленный новый STL или убранный прежний сбрасывает единицы.
- `POST /jobs/{id}/answers` принимает `{expected_revision, answers}`. Ключи это id вопросов текущей карточки, ответ можно изменить. «Не знаю», «неизвестно» и пустой ответ сохраняются одним значением «Не знаю» и ответом не считаются.
- `POST /jobs/{id}/control/{stop|retry}` останавливает или повторяет обработку.
- `GET /jobs/{id}/events` отдаёт SSE с поддержкой `Last-Event-ID`. Без курсора поток начинается с текущей ревизии. Новые события приходят по `LISTEN/NOTIFY` PostgreSQL сразу после коммита, без опроса базы.
- `GET /jobs/{id}` отдаёт снимок без полного отчёта STL; он есть в `GET /jobs/{id}/card`.
- `GET /jobs/{id}/card` отдаёт карточку текущей ревизии.
- `GET /jobs/{id}/artifacts/{artifact}` отдаёт страницы, проекции и отчёт STL.

## Качество на настоящей модели

`uv run --locked python scripts/eval_stage1.py "~/Downloads/Примеры деталей" [--only 1 3]` прогоняет примеры организаторов через настоящий Qwen и сравнивает карточки с фактами из `tests/eval/reference.json`. Эти факты переписаны из DOCX независимо от ответа модели. Результаты сохраняются в `artifacts/eval/<время>/`. Поле `codes` в строке сводки показывает, сколько требований карточки используют код словаря.

Прогон примера 1 от 24.10.2026: найдены все 5 эталонных фактов, оценка судьи 0.88, 17 требований, 6 открытых вопросов, из них 1 блокирующий (подтверждение значения, цитату которого код не нашёл дословно). На это ушло 20 вызовов, 332 тыс. токенов и 9,5 минуты.

## Проверки

```bash
docker compose -f compose.test.yaml up --build --abort-on-container-exit --exit-code-from tests
```

В Docker поднимаются настоящий PostgreSQL, API, воркер Procrastinate, детерминированный тестовый провайдер (`tests/model_server.py`, ответы по заголовку `X-Mosprom-Agent`) и Chromium. В этом окружении выполняются pytest с порогом покрытия 80%, Ruff, mypy, Vitest и Playwright. Для отдельных запусков: `uv run --locked pytest`, `uv run --locked ruff check .`, `uv run --locked mypy src/backend`, `npm --prefix src/web run test:unit`.

## Известные ограничения

- В базе KB-001 есть только плотности и описания материалов Stereotech и имя профиля принтера. Рабочей области принтера и тепловых свойств марок там нет, поэтому несоответствие «требование против возможностей» почти не находится.
- Один прогон на настоящем Qwen идёт около 10 минут.
- Нативная установка на Windows и проверка внутри STE Slicer не выполнены.
