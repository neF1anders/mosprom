# План команды на хакатон STE Slicer

Команда: Макс — капитан, Элен, Юля, Федор, Григорий. План составлен 23 октября 2026 года. Все часы ниже — московские. Назначения, кроме капитана, предлагаются для старта и могут быть обменены целиком с сохранением границ ответственности.

Цель: к сдаче получить устанавливаемый плагин STE Slicer и воспроизводимый комплект результатов по всем семи моделям. Конкурентное преимущество — обоснованный выбор материала и режима 3D/5D по условиям эксплуатации, реальные изменения в слайсере и доказательства результата. Место на конкурсе заранее неизвестно; этот план направляет усилия на опубликованные критерии жюри.

## Концепция

**Ассистент-технолог для STE Slicer.** Пользователь прикладывает модель и фото, описывает условия работы детали. Ассистент уточняет критически недостающие сведения, выбирает доступный материал, профиль, режим и ориентацию, применяет настройки, запускает слайсинг и сохраняет полный проект 3MF и G-code. В чате остаётся короткий паспорт решения: какие требования учтены, почему выбран этот вариант, что реально изменилось и какие ограничения остались.

При наличии времени ассистент сравнивает два допустимых варианта по результатам настоящего слайсинга. Время и расход берутся из STE Slicer; прочность, ресурс и химическую стойкость нельзя выдавать за измеренные результаты слайсинга.

## Что определяет объём работы

Главный источник — [полное задание организаторов](https://665dc1hack2026.k8s.stereotech.cloud/). Презентация дополняет его расписанием. [Командная вики](https://fedorsolodkin.github.io/mosprom-/) пригодна как обзор идей и аналогов, но её архитектура шире конкурсного задания.

Обязательно:

- Плагин для выданного STE Slicer 7.10.12 Windows, API плагина 5; Python 3.5-совместимый код и PyQt5.
- Чат как SPA HTML/CSS/JS в системном браузере, открываемый плагином через локальный сервер.
- История диалога, текст, JPG/PNG и STL/OBJ/3MF, отображение инструментов, ошибок, прогресса, времени и материала.
- OpenAI-совместимый Chat Completions API организаторов с tool calling и изображениями. Ключ вводится через настройки приложения.
- MCP: initialize, tools/list, tools/call; единый каталог схем для MCP и LLM.
- Чтение и изменение глобальных настроек и настроек экструдера; перечисление, выбор, создание и сохранение профилей; работа с материалами.
- Загрузка, перечисление, перемещение, поворот, масштабирование, расстановка, удаление моделей и получение габаритов.
- Запуск слайсинга, статус, прогресс, результат, экспорт G-code и сохранение полного проекта 3MF.
- Только разрешённые режимы: classic — 3D, cylindrical — 5D Spiral, cylindrical_full — 5D. Основная тестовая машина — Stereotech Hybrid 530 V5.2.4.
- Результаты по каждой выданной модели: project.3mf, result.gcode, chat_*.png.

В этот хакатон не включать управление парком, отправку команд физическим принтерам, мониторинг камерой, генерацию CAD из фотографии, собственный слайсер, обучение нейросети и большой поиск по библиотекам. Они расходуют время, не закрывая обязательную проверку STE Slicer. Фото использовать как контекст и основание для уточнений; размеры и геометрию получать из модели.

Из вики полезны идеи прозрачных вызовов инструментов, сравнения настроек и ограниченного выбора по данным слайсера. Orca/Prusa/Cura CLI и готовый современный Python MCP SDK не заменяют требуемый плагин. ИИ-чат уже есть у [JusPrin](https://www.obico.io/blog/introducing-jusprin-first-genai-3d-printing/), поэтому одной этой функции для убедительной новизны мало.

Для начала распределить каталоги: Григорий — `plugin/AIAssistant.py`, `plugin/bridge/`; Макс — `plugin/agent/`, `plugin/mcp/`, `contracts/`; Федор — `plugin/planning/`, `knowledge/`; Элен — `plugin/web/`; Юля — `plugin/export/`, `tests/`, `scripts/`, `results/`. Это предлагаемая структура будущего кода, а не уже созданные модули. Общие точки подключения меняет их владелец по согласованному контракту.

Макс выделяет регулярные короткие окна на координацию; Юля ведёт выпуск сборок. Все изменения не должны ждать единственного человека. Изменение контракта согласуют его владелец и затронутый участник; локальные решения внутри модуля принимает его владелец. Спор о приоритете дольше 10 минут завершает Макс, записав решение.

Windows пока не закреплена за участником. Макс находит основную и резервную машину в первый час. Григорий отвечает за интеграционную проверку на основной; Юля — за повторную установку на резервной. При необходимости они работают удалённо на машинах других участников. Физический принтер не является условием приёмки, описанным в задании.

## Первые девяносто минут команды

1. **0–15 минут.** Вместе прочитать обязательные требования и закрепить владельцев. Макс заносит сроки и ссылки в общий чат, выясняет Windows-стенд и конкретные слоты в личном кабинете.
2. **15–45 минут.** Григорий запускает выданный дистрибутив, активирует 5D и подключает минимальный плагин. Макс и Элен фиксируют формат сообщения и событий. Юля готовит таблицу семи моделей и проверяет ручное сохранение проекта. Федор разбирает условия эксплуатации и каталог материалов.
3. **45–90 минут.** Первый общий проход: из чата запросить фактические параметры сцены и изменить один параметр. Параллельно проверить хотя бы ручной 5D-слайсинг. Сохранить первый 3MF как полный проект и открыть его повторно.

Если 5D не запускается вручную, Григорий и Макс сразу собирают ошибку и обращаются к эксперту. Остальные продолжают независимые модули. Подключение нового движка не устраняет этот блокер: проверяться будет выданный STE Slicer.

К концу первых 90 минут должны быть согласованы только необходимые общие сущности: идентификатор задания, объект сцены, файл, вызов инструмента и его результат, план изменений, состояние слайсинга. Зафиксировать единицы, систему координат, шкалу прогресса и значение успешного результата. Вызов, который только поставил операцию в очередь Qt, ещё не означает, что операция завершена.

## Как работать с кодовыми агентами

**Единица работы — проверяемый результат на 1–3 часа.** В общей доске достаточно состояний «готово к работе», «в работе», «проверка», «готово» и отметки блокера. У каждого человека одновременно одна основная задача. У задачи есть владелец, разрешённые файлы, вход, выход, зависимости и способ приёмки.

Каждый агент получает одинаковое краткое описание ограничений: Python 3.5, PyQt5, STE Slicer API 5, доступные режимы, фактические профили, работа со сценой через главный поток Qt. Это предотвращает появление несовместимых f-строк, dataclasses, современных SDK и придуманных API.

Шаблон постановки задачи агенту:

> Реализуй конкретный результат [описание]. Изменяй только [каталоги]. Вход и выход соответствуют [контракту]. Соблюдай ограничения STE Slicer и Python 3.5. Не меняй общие схемы самостоятельно. Сверяй API с выданными исходниками и дистрибутивом. Проверь [сценарий]. Верни изменения, результат проверки и оставшиеся ограничения.

Рабочие правила:

- У каждого участника своя ветка и свой checkout/worktree. Два агента не редактируют одну рабочую копию одновременно.
- Небольшой PR на один результат; проверяет другой участник по таблице. Код агента принимает человек.
- В `main` попадают интегрированные изменения, прошедшие проверку в пределах своего риска. Перед демонстрацией берётся известная рабочая сборка.
- Каждые 90–120 минут — синхронизация на 7 минут: что уже работает, что блокирует, что будет интегрировано следующим. Показать результат важнее отчёта о процентах готовности.
- Не оставлять интеграцию на последнюю ночь. Первый проход собрать максимально рано, затем расширять его.
- Если агент за 20–30 минут ходит по кругу, человек уменьшает задачу, даёт найденный фрагмент API или подключает владельца соседнего модуля.
- Макеты и заглушки допустимы для независимой разработки, но не считаются доказательством работы в STE Slicer.
- Схемы и зависимости фиксируются. Новый пакет или новый сервис добавляется только после проверки совместимости и пользы для обязательного сценария.

Каждая заявка на завершение содержит: commit, короткий сценарий воспроизведения, фактический результат, известные ограничения. Для операций слайсера дополнительно — версия дистрибутива и пример полученного файла либо запись экрана.

## Семь моделей как рабочая программа проверки

Названия папок организаторов явно задают 3D для моделей 1, 3, 6 и 5D для 2, 5, 7. У фигурки в имени папки режим не указан. Метки полезны для проверки, но алгоритм не должен зависеть от имени файла. Отдельно нужно уточнить, где ожидается 5D Spiral, а где полный 5D.

| Модель | Основная проверка рассуждения | Кто ведёт разбор |
|---|---|---|
| Шестерня, 3D | Высокая влажность, УФ, нагрев, жёсткость зубьев и пиковый момент; одного слова «прочная» недостаточно | Федор |
| Колесо конвейера, 5D | Трение по бумаге, износ, отсутствие следов и стойкость к очистке; отличить желательные ESD-свойства от обязательных | Федор |
| Пыльник ШРУСа, 3D | Гибкость, масла/топливо и герметичность; осесимметричность сама по себе не означает выбор 5D | Григорий |
| Фигурка | Детализация, следы поддержек, тонкие элементы, УФ и партия 15 штук; абсолютное отсутствие слоёв не гарантируется одним параметром | Элен |
| Рабочее колесо Wilo, 5D | Совместимость многочисленных численных требований к материалу; теплоноситель при 85 °C, геометрия и балансировка | Федор и Макс |
| Крыльчатка двигателя, 3D | Нагрев, низкая плотность, ударная вязкость и химическая среда; не обещать ресурс по одному G-code | Юля |
| Копирный вал Krones, 5D | Трение по POM, износ, точность рабочего профиля, моющие средства и краткий контакт с горячим клеем | Григорий |

Это распределение проверки дополняет основные роли. Все результаты собирает Юля; единообразие технологических правил проверяет Федор. Для каждой модели записать: исходное требование, кандидат материала и источник, профиль из фактического каталога, режим, ориентацию, важные настройки, нерешённые противоречия, результат слайсинга и расположение файлов.

Не подменять выбор материала универсальным PETG. В исходниках есть специализированные семейства Enduse, Fiberpart и Sealant. Наличие профиля подтверждает доступность настроек, но не доказывает химическую стойкость, долговечность и соответствие всем численным ограничениям ТЗ. Федор проверяет паспорт конкретной марки и согласует спорные случаи с экспертом.

## Приёмка и доказательства для жюри

Официальные веса критериев в предоставленных материалах не указаны. Очерёдность работы выбираем по зависимостям: установка и реальные действия → полный комплект по семи моделям → качество технологических решений → удобство и дополнительная новизна.

| Критерий жюри | Доказательство команды |
|---|---|
| Прототип | Чистая установка плагина в выданный дистрибутив; вызов из чата действительно меняет сцену и настройки |
| Основная проблема | Семь проектов и G-code, обоснование режима и материала, повторное открытие проектов. Близость к скрытым эталонам до оценки жюри неизвестна |
| Разработка и внедрение | Понятная инструкция, минимум внешних зависимостей, измеренное время подготовки в сравнении с ручным сценарием |
| Новаторские идеи | Условия эксплуатации связаны с выбором 3D/5D, ориентации и материала; паспорт содержит фактические применённые значения |
| UI/UX | Вложения, видимые действия, прогресс, понятная ошибка и способ продолжить |
| Второстепенные проблемы | Повторное использование настроек, изменение цели через чат, снижение числа ручных операций |
| Аналитика | Краткий разбор аудитории, нескольких близких аналогов и причин выбранного объёма работы |

Задача считается законченной после проверки другим человеком. Полный сценарий считается законченным, когда новый запуск чата получает результат, полный 3MF повторно открывается с теми же настройками, G-code получен штатным движком для текущей сцены, а скриншот переписки отражает этот же прогон.

Отдельно проверить: переключение 3D ↔ 5D не оставляет старые параметры без контроля; при смене сцены старый G-code помечается устаревшим; загрузка модели ожидает завершения; ошибки LLM/слайсера видны; секреты не попадают в результаты и скриншоты; большой STL не зависает в UI. Минимум несколько повторов одной 3D- и одной 5D-задачи с одинаковыми входами, плюс изменённая формулировка и переименованный STL для проверки зависимости от смысла задачи.

Публично показывать только измеренные показатели: сколько из 7 заданий завершено, сколько проектов корректно переоткрывается, сколько раз потребовалась ручная правка, сколько заняла подготовка, какие время и расход дал слайсер. Целевые значения команды — 7/7 комплектов и 7/7 повторных открытий. Это цели, а не достигнутые результаты.
