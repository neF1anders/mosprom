# Слайсинг и проверка G-code (этапы 4-6): что есть и как работает

Версия 0.2. ИИ-анализ карточки в этапе 3 не делаем: жёсткие проверки этапа 3 уже перенесены в `src/backend/validation`.

С 24.10.2026 этапы 4 и 5 встроены в конвейер: `src/backend/slicing` (план вызовов и проверка G-code) и `src/backend/infrastructure/slicer.py` (вызовы плагина), см. [PIPELINE.md](PIPELINE.md). Скрипты `tools/slicing` остаются для ручных прогонов на Windows.

## Схема

```
Этап 1: карточка ─► Этап 2: набор параметров ─► Этап 3: жёсткие проверки ─► Этап 4: применение в слайсере ─► нарезка ─► Этап 5: проверка G-code ─► ок ─► project.3mf, result.gcode
                         ▲                              │ ошибки                                                          │ ошибки по содержанию
                         └───────────── Этап 6: stage3.feedback (максимум два возврата за весь прогон) ◄─────────────────┴──── (3 и 5)
```

Возвращаться во второй этап можно **максимум два раза за весь прогон** (возвраты из этапов 3 и 5 считаются вместе). После двух возвратов берётся лучший вариант, оставшиеся замечания показываются пользователю.

## Этап 3. Жёсткие проверки (готово)
`src/backend/validation` (перенесён в #8): режим, профиль, материал 1,75 мм, ключи, типы, границы, условия `enabled`, режимные ключи, область стола, матрица поворота. Результат всегда одинаковый, ИИ не участвует.

## Этап 4. Применение в слайсере (написано, не проверено на настоящем слайсере)
`tools/slicing/apply_parameter_set.py`, тонкая обёртка над кодом конвейера (`src/backend/slicing`, `src/backend/infrastructure/slicer.py`), запуск `uv run python tools/slicing/apply_parameter_set.py набор.json --model <attachment_id>=путь.stl [--folder …] [--out-dir …] [--check] [--dry-run]`. Берёт `stage2.parameter_set` и через MCP-сервер плагина AI Assistant (ветка `feat/ste-plugin`, `server.json` с портом и токеном) вызывает инструменты по порядку:
`set_printer` → `set_print_mode` → `set_quality_profile` → `set_material` → `set_setting` (по каждой настройке) → `load_model` → повороты (`rotate_model`) → `scale_model` → `move_model` → `slice_model` → `export_gcode` → `save_project`.

- `--dry-run` печатает план без сети.
- `--check` перед применением запускает жёсткие проверки этапа 3 и при ошибках не применяет.
- Слайсер подрезает значения вне диапазона: адаптер сравнивает записанное с запрошенным и выносит расхождения в список `clamped`.
- Что плагин не умеет, адаптер помечает `unsupported`: материал не для экструдера 0, неравномерный масштаб.

Проверено: `tests/backend/test_slicing.py` против заглушки плагина `scripts/fake_ste_slicer.py`: порядок вызовов, остановка на первой ошибке, подрезка, неверный токен, разложение поворота.
Проверено на Windows 24.10 (STE Slicer 7.10.12, classic): вся цепочка до `result.gcode` и `project.3mf` проходит; сдвиг `position [30, 20]` даёт центр печати +30 по X и +20 по Y в машинных координатах (значит, Y набора это машинный Y, `move_model(x=X, z=-Y)`); поворот вокруг x на ±90 даёт ожидаемую грань вниз; масштаб; поддержки находятся в G-code; неравномерный масштаб помечается `unsupported`.
Найдено и исправлено: сцена слайсера Y-вверх, а набор в системе Z-вверх (как STL). Оси поворота переводятся: x -> x, Y набора -> z сцены со знаком минус, Z набора -> y сцены (`contract_axis_to_scene`). До правки поворот вокруг Z набора опрокидывал деталь вместо поворота на столе.
**Нет подрезки значений:** слайсер и плагин приняли `infill_sparse_density = 150` и `layer_height = 0.001` без подрезки (проверено на Windows). Границы значений проверяет только этап 3, поэтому без `--check` скрипт их не сверяет.
**Не проверено:** повороты вокруг y и z набора после правки осей (нужен повторный тест); несколько моделей; режимы 5D.

## Этап 5. Проверка G-code (готово для classic)
`uv run python tools/slicing/check_gcode.py <result.gcode> <parameter_set.json> [--iteration N] [--json]`, тот же код, что у конвейера (`src/backend/slicing/gcode.py`). Поддержки сверяются с `support_enable` набора: выключены, а в G-code есть, значит ошибка.
Потоково читает G-code (файл 15 МБ за 2 секунды) и сверяет с набором параметров.

| Проверка | Вид | Что значит |
|---|---|---|
| файл пустой, нет слоёв, нет `;End of Gcode`, не сходится `LAYER_COUNT`, нет экструзии | `file` | нарезка битая |
| режим печати, высота слоя, температуры, настройки из блока `;SETTING_3` | `apply` | слайсер записал не то, что просили (вина не этапа 2) |
| выход за стол в classic | `content` | этап 2 может поправить (ориентация, положение) |
| поддержки при требовании «без поддержек» | `content` | ограничение `support_enable = false` во второй этап |
| М140/М190 в 5D | предупреждение | в 5D стол не греется |

Итог: `ok`, `needs_changes` (есть замечания по содержанию, возвращаем во второй этап) или `apply_failed` (проблема в применении, ограничений для этапа 2 нет).

Проверено: проверка G-code покрыта `tests/backend/test_slicing.py`; два реальных G-code слайсера (`validation/data/gcode/`) дают `ok`; при изменённых `layer_height` и `infill_pattern` получаем `apply_failed` с двумя ошибками.
**Не проверено:** габариты в 5D (нет образца G-code, выдаётся предупреждение); поддержки и выход за стол на реальных G-code (только на синтетических); блок `;SETTING_3` в образцах содержит только настройки профиля, поэтому настройки, которых там нет, помечены как «не проверяемо по G-code».

## Этап 6. Обратная связь
`stage3.feedback` как в v0.1 (`constraints`, `exclude`, `warnings`), добавлены необязательные поля: `constraints[*].origin` (`rules` или `gcode`), `returns_used`, `findings` (все замечания этапа 5). `exclude` для ориентации берёт `models[0].orientation_candidate`, если этап 2 его указал; иначе в `warnings` будет пометка.
Связка «этап 3/5 → второй заход → снова проверка» **не соединена в один скрипт**.
